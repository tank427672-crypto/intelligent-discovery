# 阶段工程报告：v0.3 Knowledge + Case Intelligence Foundation

**报告对象**：项目架构负责人  
**日期**：2026-08-03  
**阶段结论**：案例知识资产基础完成；自动案例发现、验证、分析和现实跟踪仍未实现。

## 1. 当前状态

项目版本为 v0.3.0。发现、研究证据和人工反馈闭环保留；案例现在可以作为可验证、可版本化、可跨任务引用的知识资产保存。

## 2. 完成内容

- 新增 `CaseRecord`、`CaseRevision`、`CaseTaskLink`。
- 新增候选、跟踪、验证、成熟、历史的严格生命周期及独立验证状态。
- 案例强制关联原始任务的来源，可关联证据和发现；支持跨任务引用。
- SQLite 新增案例、历史和关联表；API 支持创建、读取、修订、生命周期迁移与关联。
- 报告可显示任务关联案例；案例候选发现、验证、分析、更新跟踪接口已预留。

## 3. 新增模块

`CaseService` 负责案例资产规则；`case_extensions.py` 仅定义未来的候选发现、验证、分析和更新跟踪协议。没有外部数据源、模型或社区模块进入核心。

## 4. 项目结构变化

新增 `intelligent_discovery/case_extensions.py`、`tests/test_cases.py`、`tests/test_case_contracts.py`、`docs/CASE_INTELLIGENCE.md`。现有领域、端口、SQLite、服务、API、模块目录和报告渲染器已扩展。

## 5. 数据模型变化

```text
DiscoveryTask → Source → Evidence → Finding
                              ↓
                         CaseRecord → CaseRevision
                              ↓
                         CaseTaskLink → other task
```

案例不存储版权原文，只保存来源、摘要、分析、引用关系、经验和限制。案例必须有来源；证据和发现必须来自原始任务。每次正文或状态变化保留历史版本。

## 6. 架构一致性检查

通过。案例领域对象不依赖 HTTP、SQLite、模型 SDK 或外部服务；`CaseService` 只依赖仓储端口；SQLite 是基础设施实现；自动案例能力仅为协议。机会、推荐、个人智能、社区、积分和企业模块仍保持预留状态。

## 7. 测试结果

`ruff check .` 通过；`python -m compileall -q intelligent_discovery` 通过；`pytest -q` 为 **11 passed**。新增测试覆盖案例来源/证据/发现关联、跨任务隔离、版本历史、验证前置条件、报告引用、API 创建/读取及未来提供器不得伪装验证的契约。仍有 1 条上游 FastAPI/Starlette 测试客户端弃用警告。

## 8. 技术风险

- CaseRevision 当前保存字段清单与理由，而非完整快照/差异；复杂审计将需要更强版本策略。
- 案例可信度仍由人工或未来受控提供器填写，尚无多证据加权规则。
- 跨任务链接尚不是知识图谱，不能执行全局相似案例检索。
- SQLite 适用于本地验证；并发、权限、多租户和企业审计仍未设计。

## 9. 设计偏差检查

无虚假自动案例能力。与 v0.3 完整愿景相比，Case Discovery、Verification、Analysis、Update Tracker 只定义接口而未实现，这是刻意限制：真实来源许可、验证策略和人工复核流程未获决策前不能接入。

## 10. 下一阶段建议

先完成知识检索与案例索引设计：案例字段检索、跨任务关联查询、来源版本快照和正式数据库迁移。随后选择一个许可明确的只读来源试点案例更新跟踪；不要并行启动社区或积分系统。

## 11. 需要架构负责人决策的问题

1. 哪些案例类型与来源许可证可以进入首批案例库？
2. 案例 `verified` 的最低证据数量、可信度阈值和人工复核要求是什么？
3. 版本历史应保存完整快照还是字段差异，保留多长时间？
4. 案例是否允许匿名贡献；若允许，如何处理版权、隐私、署名与撤回？
5. 知识检索先采用 SQLite FTS、PostgreSQL，还是独立搜索系统？
